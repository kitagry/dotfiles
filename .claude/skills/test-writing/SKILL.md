# テストの書き方

言語非依存の原則。言語ごとの慣行に従いつつ、ここの原則を優先する。TDD 以外 (既存コードへのテスト追加など) にも適用する。

良いテストは **仕様書として読め、リファクタに強く、失敗時に原因が一目で分かり、重要シナリオを網羅する**。カバレッジ率よりシナリオの網羅性を優先する。

## ワークフロー

1. **仕様を一行で言語化する** — 実装を見る前に「この関数は __ するもの」と書く (例:「`calculate_shipping_fee` は合計 1 万円以上なら 0 円、未満なら 500 円を返すもの」)。一行で言えないならまだ書かない
2. **シナリオを列挙する** — happy / edge (境界・空・上下限) / error を仕様だけから導く。実装を見ないと思いつかないシナリオは実装詳細依存を疑う
3. **1 シナリオ 1 テストで書く**
4. **self-review** — いずれかが No なら書き直す
   - 実装を隠して仕様だけ見せられても書けるか
   - 振る舞いを変えずに内部を書き換えても通るか
   - 失敗時にテスト名 + assertion から何が壊れたか分かるか
   - モックは外部依存だけか

## 原則

- **モックは外部依存のみ** — 外部 API / DB / FS / ネットワーク / 時刻 / 乱数だけ。内部クラスやビジネスロジックはモックしない (呼び出し順を写すだけになりリファクタで壊れる)。実オブジェクトで組むのが辛いなら設計を疑う
- **fixture より inline** — テストデータはテスト関数内に書く。例外は assertion に関係ないダミー (認証済みユーザーの雛形等) と重い共通 setup (DB コンテナ等)
- **DAMP 寄り** — 本旨と無関係なセットアップは helper 化してよいが、入力・期待値・振る舞いはテスト関数内に書く
- **1 テスト 1 シナリオ** — 複数 assertion は同じ振る舞いの別側面に限る。テスト名に `and` が入ったら詰め込みすぎ
- **テスト名は行動を平文で** — `TestCalculateTotal_ReturnsZeroWhenListIsEmpty` / `test_returns_zero_when_list_is_empty`。`test_1` / `test_success` は NG
- **Table-driven / parameterize を積極活用** — 同じ入力形式で期待値だけ違うものに使い、各ケースに名前を付ける。setup や観点が違うシナリオは無理にまとめない
- **入力値はシナリオを語る** — `[]` は空、`0` / `-1` / `MAX_INT` は境界、`"not-an-email"` は不正入力、と値で意図が伝わるものを選ぶ
- **assertion の情報量を最大化** — 構造体はフィールドごとでなく丸ごと比較する (予測不能なフィールドだけ除外)。message を付けるか、`cmp.Diff` / Jest 等の自動 diff を使う

## アンチパターン

- **実装のミラーテスト** — 実装のロジックや定数を写す。`assert discount(100) == 100 * 0.8` ではなく、仕様から導いたリテラルで `assert discount(100) == 80`
- **モックだらけ** — mock が 3 個以上、assertion が `called_with` ばかりで返り値/副作用を見ていない。外部依存だけ InMemory 実装等に差し替え、他は本物を使う
- **詰め込みすぎ** — 属性設定・ID 採番・デフォルト値を 1 テストで見る。シナリオごとに分ける
- **ライブラリの振る舞いのテスト** — ORM の save→find、HTTP クライアントの status 等。削除し、自分のコードがライブラリをどう使うか (引数の組み立て/結果の解釈) だけを検証する
- **実装を先に読んで書く** — ワークフロー 1 (仕様の言語化) を先にやって防ぐ
