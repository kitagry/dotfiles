# TDD - リファクタリングフェーズ

テストが通っている状態から始め、1 つ改善するごとにテストを実行する。

1. **対象を探す**: 重複、読みにくい処理、不適切な命名、長すぎる関数、マジックナンバー/文字列
2. **既存コードとの凝集を確認する**（今回書いたコードの中だけで完結させない）
   - 新しい型を作った、または `int64` / `string` 等の素の値に名前付き型を付けたら、**その値を引数・戻り値で扱う既存関数を探す**。その型のメソッドにできるなら寄せる（例: `FormatBytes(int64)` → `ByteSize.String()`）
   - テストに**同じ概念の逆向きの変換**（parse と format、encode と decode、validate と表示）が両方出てきたら、同じ型・モジュールに置けないか検討する
   - 寄せた結果、パッケージの依存の向きがおかしくならないか確認する（例: 汎用の表示処理が特定機能のパッケージに依存するなら、型を共有パッケージに置く）
3. **やりすぎない**: 将来の要件のための抽象化・早すぎる最適化・不要なデザインパターンは入れない。新しいヘルパーは 3 回使われるまで作らない (Rule of Three)
   - Rule of Three は「新しいヘルパーを作るか」の基準。**既存コードと同じ概念を 1 つの型・モジュールに寄せる作業は対象外**で、むしろ積極的に行う

終わったら `tdd-workflow` の「レビュー」へ。次の機能は再び `/tdd:red` から。
